关于 Display Master

示意图。一台屏一张卡、横向并排：卡右上角是「开启」和「HiDPI」两枚开关，分隔线下面是亮度、分辨率两条对齐的滑块。被关掉的内置屏（最右）依然是这排里的一员，只是整张卡灰了、两枚开关都落在关的位置 —— 点卡片主体才进这台屏的详情页。

它能帮你做什么

系统设置里顾不到的那几件小事，这里都补上了。

单独开关某台显示器

关掉之后，这块屏会从桌面布局里退出去，窗口自动挪到还在用的屏幕上。想用回来的时候， 它还在原来那张卡片上 —— 把「开启」拨回去就亮，不会跑到别处去。

亮度、分辨率，两条对齐的滑块

一台屏一组独立滑块，打开菜单直接拖，不用先展开一层，也不会拖错屏。分辨率那条和亮度 严格左对齐，轨道上的格子点就是可选档位，拖动时只改数字、松手才真正切换。 内置屏亮度用系统接口，外接屏走 DDC/CI，写入做了节流，不会把通道写坏。

键盘 F1 / F2 也能调

按笔记本上那两个亮度键就能调外接屏，一次 6%，调的是鼠标指针所在的那台显示器， 屏幕上会有一个小浮层显示当前档位。媒体键和普通功能键两种键盘都接 —— 第三方机械键盘的 F1 / F2 也照样能用（系统设置里那句「把 F1、F2 用作标准功能键」 只对苹果键盘有效）。这个功能需要「辅助功能」权限：亮度键是系统级媒体键，想接管只能建事件监听， MonitorControl 这类工具都是同一套做法，macOS 至今不原生支持。第三方键盘那条路走的是 只读监听，吞不掉任何按键 —— 这不是「我们写得小心」， 而是系统 API 契约：只读监听根本拿不到修改权。授权是可选的：关掉那行开关， F1 / F2 立刻交回系统原样。

HiDPI 一键切换

开关在卡片右上角，就在「开启」下面。当前跑在哪种倍率看分辨率那一行右端 —— 是 HiDPI 档位时数字后面会跟一枚 HiDPI 小标签。 分辨率不用变就能把渲染精度提上去时最省事；有些屏没有同样尺寸的高分档位， 开关会灰掉拨不动 —— 那就去详情页的全部分辨率里挑一档。

分辨率滑块

轨道上的格子点是筛过的档位：只留和面板原生比例一致的那一批， 同一逻辑宽度优先给 HiDPI 那版，所以一屏十来档、一格一格拖得准。 想看完整列表（包括会改变长宽比的偏门档位），去详情页的「全部分辨率」， 最下面还有一枚「显示所有分辨率」。

DDC 通道自检

亮度怎么都调不动的时候，可以在终端里跑一次 --ddc-test。它会把读、写、复读、恢复走一遍，读数没变，就说明确实没写进去。

纯 Swift，不联网

整个应用用 AppKit 和 CoreGraphics 手写，没有第三方依赖，也没有内核扩展。不联网， 默认不申请任何系统权限 —— 唯一例外是「用 F1 / F2 调亮度」这个可选功能 （接管系统级媒体键需要辅助功能权限），开关关掉就与权限彻底无关。代码量不大，想读的话一个下午能过一遍。

v1.6.4 普通按键通道改成「只读」，并把「不会弄坏键盘」变成可复跑的检查

普通按键通道改成「只读」，并把「不会弄坏键盘」变成可复跑的检查。 1.6.3 为了让第三方键盘的 F1/F2 生效，把 keyDown / keyUp 挂进了一个活动型 事件监听（能吞事件的那种）。真机上用户报「外接键盘打不了字了」—— 一个活动型 tap 只要回调被卡住、或被系统停用，整个键盘的输入都会被扣住， 而这条通道换来的不过是「少调一次内置屏亮度」。 收益极小、爆炸半径极大，这个交易不该做： 回调返回值被系统忽略 —— 从结构上就不可能吞掉任何按键。 代价写进文档：普通 F1 / F2 会被别的应用同时收到（对这类键盘来说那是本来 就有的行为，不是我们引入的）。 与不会弄坏键盘的 1.5.x/1.6.0 时期完全一致。 以前是在事件回调里直接调用的 —— 那正是「回调超时 → tap 被停用 → 键盘被扣住」 这条链的起点。现在回调只做限频判断（加锁查一次表），日志一律异步落盘。 宁可失去这个功能，不能连累键盘；上一次是硬撑着不认输，用户只能靠 pkill 自救。菜单那行开关可手动重试（重试会清掉看门狗的判决）。 投三种合成事件（普通按键 / 标准 F1 / 亮度媒体键），检查「普通按键与 F1 穿过、 亮度键被拦下」。把「不会弄坏键盘」从口头承诺变成一条机器能反复跑的断言。 （缺「输入监控」权限），并在授权后 3 秒内自动接上。

  • 普通按键通道改为 .listenOnly（只读型）。按 API 契约它拿不到修改权，
  • 活动型 tap 的掩码只剩 NX_SYSDEFINED 一个位。它物理上碰不到普通按键，
  • 回调里不再做任何文件 IO。ruleLog 是同步文件 IO（开句柄 → seek → write），
  • 看门狗：tap 在 60 秒内被系统停用 3 次，就主动退出接管并留一条日志。
  • --key-audit 新命令：在我们自己的两条 tap 之后挂一个尾部只读探针，
  • --hotkey-status 与自检新增「吞键范围」一行；F 行通道单独失败时会报出原因

v1.6.3 修「按 F1 / F2 毫无反应」的真正根因：按键走的不是我们接的那条通道

修「按 F1 / F2 毫无反应」的真正根因：按键走的不是我们接的那条通道。 上一版加的 --sniff 一测就清楚了。同一句「按 F1」，不同键盘走的路完全不一样： | 键盘的 F 行行为 | 发出来的事件 | 原来接不接 | |---|---|---| | 媒体键（苹果键盘默认、部分键盘的多媒体模式） | NX_SYSDEFINED keyType=2/3 | ✅ 接 | | 标准功能键（多数第三方机械键盘的出厂状态） | 普通 keyDown keyCode=122/120 | ❌ 没接 | 真机实测（MCHOSE X75 V2）：F1 / F2 / fn+F1 / fn+F2 八次按键全部是标准功能键码， 一次 NX_SYSDEFINED 都没有。所以权限、监听、键码解析、目标屏四项全对， 日志老老实实写着「已接管」，而按键压根没走那条路 —— 这类故障最难查， 因为每一环单独看都是好的。 按下与抬起都吞（只吞按下会留下没有配对的抬起）。 fn 不算修饰键，按住 fn 再按 F1 一样生效（很多键盘的多媒体模式就是 fn+F 行）。 （表现是「按一下跳两格」）。媒体键通道刚处理过（60ms 内），普通按键通道就让路。 默认开是因为这类键盘的 F1/F2 本来什么也调不了（系统没接、别的应用也没接）， 默认关就等于「装完还是按了没反应」。代价写清楚了：不带修饰键的普通 F1/F2 会被吞掉， 需要给别的应用用的把这一项关掉即可，媒体键通道照旧工作。 诊断同步： 这两种状态在「已接管」这个结论上长得一模一样。

  • 新增第二条输入通道：连同普通按键里的 keyCode 122（F1）/ 120（F2）一起接管，
  • 带 ⌘ / ⌃ / ⌥ 的不抢：⌘F1 这类是别的应用的快捷键，抢掉等于改坏键盘布局；
  • 去重：个别带厂商驱动的键盘一次按键会同时发两种事件，那就会走两条路各调一次
  • 新开关「接管标准功能键 F1 / F2」，默认开，只在主开关打开时出现。
  • --send-key f1|f2 —— 发普通按键通道的合成 F1/F2，用来验证这条新路（原先只有 up/down）。
  • --hotkey-status 增一行「接管通道」，直接报出接的是媒体键还是两条都接 ——
  • 事件留痕分通道前缀（亮度键·收到（普通按键）…），排查时一眼看出按键从哪条路来。

常见问题

下面这些基本都是在实际使用里踩出来的，按遇到的频率排了序。每条会先说清原因，再给办法， 尽量不写「请重试」这种没什么信息量的建议。

外接屏的亮度滑块没反应，显示「亮度不可控」

按这个顺序试一遍，大多数情况在第一步就好了：

  1. 先在显示器自己的按键菜单里找找有没有 DDC/CI 开关。 不少显示器出厂时默认把这个功能关着，关着的时候一律不应答。 打开之后，回到应用里点一下「重新检测 DDC」。
  2. 换一根线试试。 走某些 USB-C 扩展坞、KVM 切换器、HDMI 转接头的链路，可能会把 I²C 通道吃掉， 直连一般就好了，比如用显示器原装的那根 DP 线。
  3. 跑一次 --ddc-test 看具体卡在哪：
    终端
    "/Applications/Display Master.app/Contents/MacOS/DisplayMaster" --ddc-test
    它会把读数 → 写入 → 复读 → 恢复的全过程打印出来。读得到、写不进去，是时序问题（本应用已按 MonitorControl 的时序参数实现）；根本读不到，那就是上面两条链路或者显示器设置的问题。
  4. 确认一下这台显示器支不支持 DDC/CI。 便宜的老显示器、部分电视，还有绝大多数走 HDMI 接入的屏幕都不支持， 这种情况软件层面帮不上忙。

亮度突然调不动了，或者说「显示器未应答（空报文）」

这是 DDC 通道被过度密集的写入写死了。显示器本身还在正常工作，只是它的 DDC 控制器不再应答请求。

1.0.1 起不用你动手：读写一旦无应答，应用会自动重建一次 DDC 通道再重试。 重建相当于热插拔时系统自己做的事，比给显示器断电温和很多，也快很多。 如果你还在旧版本上，用下面这个办法自救，一般一次就好，不用拔线，也不用断电：

  1. 找到那台显示器的那张卡，把卡右上角的「开启」开关拨到关。
  2. 等一两秒，再把同一张卡上的「开启」拨回去。卡片不会跑到别的地方去，就在原来那一排里。

上面这招不管用的话，再考虑给显示器彻底断电几十秒。注意是拔电源，不是拔视频线， 拔线没用，I²C 控制器在 Mac 这一侧。

这个应用已经尽量在避免这件事

写入节流（外接屏最少间隔 0.1 秒）、读取节流（最少间隔 2 秒）、失败后自动冷却 20 秒、 失败时自动重建通道再重试，这些都是为了让通道别被写死。极端情况下仍然可能触发， 所以留了上面这个一键自救的办法。

显示器睡眠 / 唤醒之后，亮度滑块没反应了

这是 1.0.1 修掉的主要问题之一，原因还挺反直觉：显示器睡眠唤醒之后， DDC/CI 的 I²C 通道会「哑掉」，句柄还在、调用也不报错，但读不出也写不进。 1.0.1 之前，这个状态被几处细节卡死了（唤醒瞬间重新枚举服务失败会把句柄列表清空， 失败冷却又把写入一起挡住），于是滑块还在，拖了却纹丝不动。

现在它会自己恢复：应用会监听系统的唤醒与屏幕配置变化通知，唤醒后自己重建 DDC 通道； 就算通知漏了，下一次读写失败也会触发同样的自愈。你不用做任何操作， 菜单里的「重新检测 DDC」现在只是手动兜底。

要是唤醒后滑块那一行显示「无应答」，说明这次自愈没成功，比如显示器真的死机了。 点那张卡进详情页，点一次「重新检测 DDC」；还不行就给它断电重启。

打开一台已关闭的显示器之后，那张卡片还是灰的

这也是 1.0.1 修掉的问题。两个原因凑到了一起：

  • 系统在屏幕睡眠时修改显示配置会返回一个错误码（实测是 1014，而不是表示成功的 0）， 但配置其实已经生效了。旧版本只看这个返回值，就以为「没打开成功」，于是那条「已关闭」记录不删 —— 菜单里就一直多一张灰卡片。
  • 显示器重新上线时系统可能给它分配一个新的 displayID， 只按 id 记账的记录就永远清不掉了。

1.0.1 改成以实际结果为准：动作发出去之后轮询在线列表，看显示器是不是真的回来了； 「已关闭」记录还会连 EDID 三要素一起存下来，换 id 也认得出同一台屏。 另外现在会先唤醒屏幕再改配置（屏幕上能出现菜单，说明人就在机器前）， 列表也改成以 CoreGraphics 为准，因为 `NSScreen` 在一台屏被重新打开之后，实测会滞后 3 秒以上。

如果那张灰卡片对应的显示器其实已经拔线走人了，用详情页里的 「忘记这台显示器（从列表移除）」把它清掉。

关掉的显示器去哪了？怎么开回来

它哪儿也没去，还在原来那一排卡片里 —— 只是整张卡变灰、「开启」落在关的位置上。 把「开启」拨回去就亮，不用去别处找。

1.2.0 及更早的版本会把它从那一排里挪走、在菜单底部单开一行文字；那套做法已经取消了， 因为「关掉内屏之后菜单里就只剩外接屏，看不见自己刚关了什么」。

这些记录记在系统偏好设置里，所以退出应用、甚至重启电脑之后再打开，那张灰卡片都还在。 已经重新上线的显示器，对应记录会被自动清掉。

为什么重启或睡眠之后，关掉的显示器又自己回来了

因为「关闭显示器」是会话级的操作，只对当前这次登录有效。显示器睡眠、屏幕休眠、重启，都会让配置回到系统默认的样子。

这是有意留下的安全网：万一哪次关闭之后画面不对劲，重启一下就能回到全部可见的状态，不至于把自己关在外面。 想让它跨重启保持关闭是另一个功能，需要写系统级的显示配置，目前还没做。

为什么关不掉最后一台显示器

这是特意留的一道坎：只剩最后一台还在工作的显示器时，应用会拒绝关闭，并且「嘟」一声。

不然你会得到一台没有画面、也没法操作的机器，只能盲操作或者按住电源键。

打开了「有外接屏时自动关闭内置屏」，内屏却没有关

按可能性排，一般是这几种情况：

  • 当前没有外接屏在线。 规则的前提就是「有外接屏」，没有的话它不关任何东西。
  • 屏幕正在睡眠。 只要有显示器还睡着，规则就不动手。一是系统不接受改显示配置， 二是硬来会把屏幕平白唤醒。
  • 你手动把内屏开回来过。 规则只在外接屏接上、拔掉的那一瞬间判断。 你手动开回来的内屏不会被立刻关掉；想让它重新按规则来，把外接屏拔掉再插上就行。
  • 内屏是唯一剩下的一块屏。 只剩一块时应用会拒绝关闭，这是防黑屏的保护。

想弄清楚它到底怎么判断的，跑一次 --auto-test。它会打印在线显示器、开关状态， 以及这一轮准备做什么、为什么。这个开关的完整行为见使用说明。

拔掉外接屏之后，为什么多出一台我不认识的显示器

那是 macOS 自己造的虚拟显示器。当所有真实显示器都不可用的时候 （比如内屏被关着、外接屏也拔了），系统会造一块出来维持显示输出 —— 它没有任何物理输出， 你也看不到它。

1.1.1 起应用会把它认出来并排除：菜单里不会出现，也不会被当成「还有外接屏接着」。 系统设置里可能还留着这么一台，那个不归本应用管。

拔掉外接屏，内屏没有自动亮回来

这个问题出现过两次，两次的根因都不在判断逻辑，而在「认错了屏幕」：某样东西 看着像外接屏、其实你根本看不见，规则就以为「外接屏还接着」，于是什么都不做。

版本被错认成外接屏的是
1.1.0macOS 在所有真实屏都不可用时造的虚拟显示器
1.4.0 及更早随航（iPad 投过来的屏）断开之后留下的残影 —— 名字形如「 (AirPlay)」，设备名是空的

1.4.1 起这两类都统一认成占位屏：不进菜单，也不计入「外接屏」。 同一版还把两件事一起修了：

  • 救援不再看那个开关。原来整段「把内屏开回来」都写在「开关已打开」后面， 所以没开过这个功能的人，只要在外接屏插着的时候手动关掉内屏、再拔线，同样会黑屏。
  • 内屏的 id 改成一串候选。原来只记一个，它一过期就彻底开不回来了。
  • 兜底巡检从 60 秒收到 10 秒，通知万一丢了也能在 10 秒内补上。

屏幕现在是黑的，怎么救回来

黑屏的时候菜单打不开、也点不了任何东西，但命令行还能用。直接开回来：

"$APP" --set-display 1 on

1 是笔记本内屏的 displayID，绝大多数机型都是它。不确定的话先看一眼：

"$APP" --auto-test

它会打印开关状态、在线的是哪几块屏、被排除的虚拟屏 / 占位屏，以及规则判定成什么、 理由是什么 —— 如果那一行写着「判定：打开 内置屏」，说明应用已经知道该做什么了。 再加上 --apply 就会真的执行一次。

升级到最新版之后要是仍然不亮，把日志发出来就能定位：

"$APP" --auto-log

它会打印每次判断的现场 —— 收到配置变化时在线的是什么、判定成什么、执行成没成、有没有重试。 对照一下就知道是「系统没通知到应用」还是「改了但没生效」。

前提：应用得在运行

救内屏这件事只有应用在做。退出应用之后，内屏就是关着的，再拔线也没人管 —— 所以如果你把内屏关了又打算退出应用，先在菜单里把内屏开回来。

DMG 和 zip 该下哪个

推荐 DMG。双击挂载后会弹出一个安装窗口，把左边的 Display Master.app 拖到右边的「应用程序」上就装好了，再点侧栏的推出按钮卸载磁盘。不用先解压，也不用自己去访达里找应用程序文件夹。

两边的内容完全一样，都是同一个 App，区别只在交付方式：DMG 里的 App 带着完整的代码签名， 不会遇到下面那条「解压工具弄丢元数据、导致应用已损坏」的问题。

zip 适合不想挂载磁盘映像的场景，比如用脚本自动安装。解压请用系统自带的「归档实用工具」， 或者命令行 ditto -x -k。

挂在侧栏的磁盘删不掉？

那不是文件，是一块临时的只读磁盘。在访达侧栏里点它右边的推出按钮，或者在桌面上右键它选「推出」就行。 直接把图标拖进废纸篓也可以，效果一样。

下载后提示「应用已损坏，请移到废纸篓」

先别急着删。这多半是签名或者隔离标记的问题，文件本身是好的。 原因有两种，对应两种做法：

原因一：解压工具破坏了代码签名

macOS 的 zip 里会夹带一层 ._* 元数据文件。如果解压工具把它们直接铺进了 .app 包里， 签名校验就会失败，系统据此判定它「已损坏」。

做法：删掉重新解压一次，这次用 Finder 双击 zip（走系统自带的「归档实用工具」），或者用命令行：

终端
# ditto 是 macOS 自带的，能正确处理 .app 的元数据
ditto -x -k DisplayMaster-1.0.1.zip .

原因二：文件带着下载隔离标记

从网上下载的文件会被打上 com.apple.quarantine 标记，未签名的应用带着这个标记就会被拦下来。 去掉它就行：

终端
sudo xattr -dr com.apple.quarantine "/Applications/Display Master.app"

更多细节，以及另外两种更省事的办法，见安装说明。

为什么不能上架 App Store

因为它调用了 macOS 的私有接口，具体是 CGSConfigureDisplayEnabled（来自 SkyLight 框架）。 「单独关闭某台显示器」这件事没有公开 API 可用，只能靠私有符号。

这些符号是用 dlopen / dlsym 在运行时取出来的，构建时并不链接任何私有框架。 好处是 Apple 哪天把符号改掉了，应用不会直接启动失败，只会「关屏」这一个功能失效，其它功能照常。

随时可以跑 --selftest 确认这些接口在当前系统上还在不在。

它会不会联网、会不会收集数据

不会。整个应用没有一行网络请求代码，也不要任何系统权限（不用辅助功能、不用屏幕录制、不用完全磁盘访问）， 更不写日志文件。

它在磁盘上唯一留下的东西，是系统偏好设置里的一条记录，内容是「你关过哪几台显示器」，用来在菜单底部留个恢复入口。 想清掉它：

终端
defaults delete com.zed.displaymaster 2>/dev/null; echo "已清理"

代码量不大，不放心的话可以直接翻一遍。

在 Intel Mac 上能用吗

能跑，不过有一处功能是缺的，先说清楚比较好。

发布的是通用二进制，Apple Silicon 和 Intel 都能启动。 开关显示器、分辨率、HiDPI、内置屏亮度这些都正常。

外接屏的亮度用不了。 它走的是 IOAVService 这个私有框架， 而它只存在于 Apple Silicon。Intel 机器的 DDC 要另走一套 IOI2CInterface，这部分没有实现， 菜单里那台外接屏的亮度位置会写「亮度不可控」。

还有件事得说明白：开发和验证都是在 Apple Silicon + macOS 26.6 上做的，Intel 路径没有实机测试过。 如果你在 Intel 上遇到别的问题，欢迎开一条 issue说说情况。

接了两台同型号的外接屏，亮度会串吗

按现在的实现，是有可能出现串屏的，说清楚比较好：

现在是把 DDC 服务按顺序跟显示器配对的。只有一台外接屏时，序号和显示器一一对应，不会有问题。 但如果接了两台同型号的外接屏，应该改成按 EDID（每台屏唯一的那串标识）来配对，这部分还没做。

如果你正好是这种配置，又碰上了亮度串屏，欢迎开条 issue， 把两台屏的 EDID 信息（--selftest 的输出）附上就好。

关掉显示器会把我正在用的窗口搞乱吗

会重新排列，但不会丢。窗口会像你拔掉那台屏的线一样，被挪到剩下的显示器上； 重新打开那台屏之后，窗口一般不会自动回到原位，得自己拖回去。

它改的是真正的显示布局，这跟「盖一层黑图」是两回事。用之前最好先把正在全屏的应用退出来。

和 BetterDisplay、MonitorControl 是什么关系

没有代码上的关系，只是思路参考。三个项目各自解决的是不同的问题：

项目特点
Display Master 免费、开源、代码量小。就做三件事：单独开关屏、亮度、HiDPI / 分辨率
BetterDisplay 功能强大得多（虚拟屏、XDR 亮度、色彩配置……），不过「显示器连接/断开」是付费 Pro 功能
MonitorControl 专注外接屏的亮度和音量，支持键盘快捷键，成熟稳定

这个项目最初就是为了替代 BetterDisplay 那个付费的「断开显示器」功能， DDC 时序参数则参考了 MonitorControl 的 Arm64DDC 实现。

怎么反馈问题

去 GitHub Issues 开一条就行， 带上下面这些信息会快很多：

  • macOS 版本、机器型号（Apple Silicon 还是 Intel）
  • 显示器的品牌型号、用什么线接的、中间有没有扩展坞
  • --selftest 和 --ddc-test 的完整输出
  • 你希望它怎么做，以及它实际是什么表现

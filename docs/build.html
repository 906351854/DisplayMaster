从源码构建

Swift Package Manager 工程，没有 Xcode 项目文件，也没有第三方依赖，一条命令就能构建完。 这一页还给想改代码的人留了几个「踩过才知道」的注意点。

需要什么

  • macOS 14 或更高
  • Xcode 命令行工具（xcode-select --install），不需要完整版 Xcode
  • Swift 5.9+（命令行工具自带）

构建

终端
git clone https://github.com/906351854/DisplayMaster.git
cd DisplayMaster
./build.sh

build.sh 会依次做完这些事：

  1. 从 AppInfo.swift 读出版本号（按文件名在 Sources/ 下查找，路径不写死）； 应用名与 bundle id 目前仍写死在脚本顶部
  2. swift build -c release 编译（带 --disable-sandbox）
  3. 组装出标准 macOS 应用包：Contents/MacOS、Contents/Resources、Info.plist （LSUIElement = true，所以没有 Dock 图标）
  4. 做 ad-hoc 签名（codesign -s -）
  5. 用 ditto 安装到 /Applications，并重启正在运行的实例

不想装到系统里，加上 --no-install，产物会留在 build/：

终端
./build.sh --no-install
open build/   # 产物在这里

也可以只用 SwiftPM 裸编译（不带应用包，适合快速验证能不能编过）：

终端
swift build -c release --disable-sandbox

命令行诊断模式

应用二进制同时还是个诊断工具。界面上的东西不好脚本化，所以验证全做成了命令行参数。 改完显示相关的代码，靠这几条命令就能确认没写坏。

参数做什么
--selftest 逐项报告：私有符号能否加载、检测到几台显示器、每台的模式数与亮度接口是否可用。排查环境问题从这条开始
--dump-menu 不打开菜单，直接把整棵菜单树按层级打印出来。菜单是懒加载的，这个模式让「菜单能不能正常构建」变成可测的
--auto-scenarios 把屏幕判定逻辑（认虚拟屏 / 占位屏、有外接屏时关不关内屏、拔掉后救不救得回来、救援候选 id 的顺序）跑一遍构造好的场景，不接触真实硬件
--auto-test 用真实状态跑一遍自动规则并打印判定与理由，不动屏幕。加 --apply 才真的执行一次；加 --on / --off 顺便拨开关；加 --fake-no-external 把外接屏一律当成占位屏，用来在真机上复现「拔线后只剩随航残影」那一幕
--auto-log [N] 打印自动规则的运行记录：每次配置变化时在线的是什么、被排除的虚拟屏 / 占位屏、判定成什么、执行成没成。黑屏这类问题，这条的输出基本就能定论
--set-display <id> on|off [--force] 直接开关某块屏。屏全黑时的救命命令（--set-display 1 on 就是开回笔记本内屏）。--force 会绕过「不许关掉最后一台」的保护，只在确认能开回来时用
--shot-menu <out.png> 把真实菜单弹出来并截一张图。改菜单外观时用它核实「画出来到底长什么样」。加 --page2 <displayID> 开在详情页，--fake-cards N 造 N 台屏验证分页
--hits 弹出菜单后把每个可点行的屏幕坐标打出来，并保持菜单不关。用合成点击做自测时靠它精确命中 —— 截屏量出来的坐标能差几十点，点空了会伪装成「这行本来就不能点」
--hidpi-test 只计算「HiDPI 开关会切到哪一档」，不做任何改动。用来确认判定逻辑
--hidpi-test --apply --all 真的逐台切一遍 HiDPI 再恢复。会短暂黑屏，属正常
--ddc-test 读亮度 → 写一个新值 → 复读 → 恢复原值。复读的数值真的变了，才说明写入生效
--ddc-storm 模拟快速拖滑块，100 次高频调用，验证节流是否把显示器写死
--ddc-recover-test 伪造「通道哑掉」（丢掉句柄 + 进入失败冷却），验证读写能否自动重建通道救回来
--toggle-test 关掉一台显示器再打开，检查「已关闭」记录是否被正确清掉。默认拿内置屏当靶子，加 --external 换外接屏
--wake-test 让显示器睡下去再唤醒，检查唤醒后 DDC 通道是否还活着。屏幕会黑几秒，可用 --sleep N 调节时长
终端
APP="/Applications/Display Master.app/Contents/MacOS/DisplayMaster"
"$APP" --selftest

类体被拆在多个 extension 文件里（DisplayManager+*.swift、AppDelegate+*.swift）。 Swift 的 private 只到文件级，所以跨文件用到的成员是 internal；存储属性必须留在类体里， 因为 extension 不能新增存储属性。这两点在每个 core 文件开头都写明了。

改代码前必须知道的两件事

这两条都是花了时间才搞明白的，不知道的话会很难查。

一、CGSConfigureDisplayEnabled 的第一个参数是配置事务，不是连接 ID

它的签名看起来像 (连接ID, 显示器ID, 开关)，于是很容易顺手传 CGSMainConnectionID()。 结果是直接崩在 SLSConfigureDisplayEnabled 里，看不到任何有用的报错。

正确做法是用公开的配置事务把它包起来：

正确调用顺序
CGBeginDisplayConfiguration(&config)          // 拿到事务句柄
CGSConfigureDisplayEnabled(config, displayID, false)   // 传事务，不是连接 ID
CGCompleteDisplayConfiguration(config, .forSession)    // 提交

另外注意最后一步用 .forSession：配置只在当前登录会话有效，不会写进系统级设置。这正是我们希望的行为。

二、枚举显示模式必须带 kCGDisplayShowDuplicateLowResolutionModes

不带这个选项调 CGDisplayCopyAllDisplayModes，在内置 Retina 屏上只会返回 3 个老式缩放模式， 连当前正在用的那个 HiDPI 模式都不在列表里，分辨率菜单于是就是错的。

带上之后，外接 5K 屏的返回数量会从 273 个涨到 648 个，去重后还有 220 项。所以代码里配了一份「常见分辨率白名单」， 默认只显示常用档位，完整列表放在「显示所有分辨率」开关后面。

重新生成图标

图标文件已经提交进仓库，正常构建不需要动它。想换图标的话，把你的方形素材（建议 1024×1024 以上）覆盖到 Resources/Logo.jpg，然后：

终端
swift Tools/make-icons.swift .

会重新产出两样东西：带圆角遮罩的完整应用图标（整个 .iconset → .icns）， 以及 18 / 36 / 54 px 三档单色菜单栏字形（这些会被当作 template 图，由系统按菜单栏明暗自动反色）。

顺便更新官网用的图标

官网首页用的是 docs/icon.png。换 logo 时记得把它也替换掉，建议导出成 512×512 的 PNG。

打包一个可发布的版本

一条命令就能打出 DMG 安装包：

终端
./build.sh --dmg

# 产物：
#   build/Display Master.app
#   build/DisplayMaster-1.0.1.dmg

DMG 里放着 App 本体、一个指向「应用程序」的快捷方式、一张窗口背景图、一个卷图标， 以及一份决定「窗口多大、图标摆在哪、背景用哪张图」的 .DS_Store。 用户双击挂载、把左边的图标拖到右边的「应用程序」上就装完了。

窗口布局为什么不用 Finder 脚本

DMG 的窗口布局只能存在 .DS_Store 里，而这个文件平时只能让 Finder 自己写出来， 也就是得用 AppleScript 驱动 Finder，那需要「自动化」权限（系统设置 → 隐私与安全性 → 自动化）。 对别人 clone 下来跑构建来说，这太脆了。

所以 Tools/make-dsstore.py 直接把这个文件拼出来，零授权、可重复。它需要两个小包：

终端
pip install ds_store mac_alias

没装也不会失败：脚本会退回用 AppleScript 驱动 Finder；再不行就产出一个窗口样式朴素 但功能完好的 DMG（拖拽安装、卷图标都在）。加 --no-layout 可以主动跳过布局。

想额外给一个 zip

同一个 Release 里也可以放 zip，方便不想挂载磁盘映像的人。打包请用 ditto，不要用 zip 命令：

终端
# -c 创建、-k 用 zip 格式、--sequesterRsrc 把元数据单独存放、--keepParent 保留外层目录
ditto -c -k --sequesterRsrc --keepParent \
  "build/Display Master.app" \
  "build/DisplayMaster-1.0.1.zip"

用 zip 或某些图形解压工具打出来的包，会把 ._* 元数据文件铺进 .app 内部， 破坏掉代码签名封印，用户下载后就会看到「应用已损坏，请移到废纸篓」。ditto 会正确处理这件事。

之后在 GitHub 上打个 tag、把安装包传进 Release 就行：

终端（需要装 gh）
git tag -a v1.0.1 -m "Display Master 1.0.1"
git push origin v1.0.1

gh release create v1.0.1 \
  "build/DisplayMaster-1.0.1.dmg" \
  "build/DisplayMaster-1.0.1.zip" \
  --title "Display Master 1.0.1" \
  --notes "首个公开版本"
发版时记得同步版本号

版本号写在 Sources/DisplayMaster/Support/AppInfo.swift，build.sh 按文件名找到它、读出来填进 Info.plist（所以这个文件以后挪位置也不用改脚本），官网也会自动从最新 Release 读取版本号。 改一处就够了，但别忘了改。
